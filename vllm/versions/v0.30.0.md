# vLLM v0.30.0 Source Audit

Release: 2026-09-22  
Upstream: https://github.com/vllm-project/vllm/releases/tag/v0.30.0

## 1. Executive assessment

v0.30.0은 v0.29의 **MRV2 default inversion을 다시 뒤집는 release가 아니라, 그 execution path를 production-scale로 확장하고 hardening한 release**로 보는 것이 정확하다.

0.26 baseline에서 특히 중요한 변화는 다음이다.

- v0.30 공식 기본 CUDA artifact는 CUDA 13.0이며 CUDA 12.9 artifact도 별도 제공됨. 이는 v0.30에서 처음 도입된 변화라기보다 0.26 baseline에서 직행할 때 반드시 격리해야 하는 runtime delta임
- KV connector dependency가 NIXL 1.4.1로 상승
- Mooncake package가 CUDA major에 따라 package variant까지 갈림
- MRV2에서 DBO, PP speculative decoding, adaptive verification, CUDA Graph startup/correctness가 크게 확장
- PCP/DCP/P-D 조합과 hybrid Mamba disaggregation이 본격 확대
- scale-out API가 plain `vllm serve`에서 opt-in으로 변경
- Fast Start(`ipc_cache`)라는 별도 weight lifecycle이 추가
- Kimi K3/Qwen3.8/DeepSeek V4/GLM 5.x 계열의 model-specific path가 계속 빠르게 변경

따라서 0.26 -> 0.30 migration은 단순 package bump가 아니다.

```text
runtime artifact
+ model runner
+ graph/memory accounting
+ recurrent-state cache
+ KV transfer dependency
+ frontend endpoint exposure
+ model-specific kernel path
```

를 다시 인증해야 한다.

## 2. Release artifact boundary: current v0.30 artifact contract

v0.30.0 공식 artifact는 아래와 같다. CUDA 13 default 자체는 이전 0.28/0.29 계열에서도 이미 존재했으므로 **v0.30 신규 feature로 분류하지 않는다.** 다만 0.26 production baseline에서 0.30으로 직행할 때 runtime isolation에는 중요하다.

```text
vllm/vllm-openai:v0.30.0        -> CUDA 13.0
vllm/vllm-openai:v0.30.0-cu129  -> CUDA 12.9
```

를 제공한다.

### Migration implication

0.26 -> 0.30에서 engine version과 CUDA major를 동시에 바꾸면 regression attribution이 어려워진다.

따라서 현재 0.26 baseline이 CUDA 12.x 계열이라면 compatibility phase는:

```text
0.26 current baseline
 -> 0.30.0-cu129
 -> 0.30.0 default CUDA 13.0
```

순으로 권장한다. 이미 baseline runtime이 CUDA 13 계열이라면 동일-major artifact를 먼저 선택한다.

첫 번째 단계에서는 vLLM semantic delta를, 두 번째 단계에서는 runtime/kernel/dependency delta를 분리한다.

## 3. KV connector dependency contract

v0.30.0 `requirements/kv_connectors.txt`:

```text
lmcache >= 0.3.9
cupy-cuda13x != 14.1.0
nixl == 1.4.1
mooncake-transfer-engine >= 0.3.12
```

또 공식 build path는 CUDA 13 image에서 동일 Mooncake release의:

```text
mooncake-transfer-engine-cuda13
```

variant로 swap한다.

### Platform implication

현재 0.26 계열의 Mooncake/NIXL artifact를 그대로 재사용하면 안 된다.

Production candidate는 최소 다음을 immutable bundle로 묶는다.

```text
vLLM image digest
CUDA major
NIXL exact version
Mooncake exact version
Mooncake package variant
Mooncake wheel SHA256
native build/runtime feature manifest
```

특히 `mooncake-transfer-engine >= 0.3.12`를 production에서 unconstrained resolution에 맡기지 않는다.

## 4. Model Runner V2: 0.29 default, 0.30 operational hardening

v0.29에서 MRV2가 일반 CUDA model의 default path가 됐다.

v0.30은 이 path 위에 다음을 확장한다.

- dual-batch overlap in eager mode
- FULL CUDA Graph microbatch path
- PP에서 MTP
- PP에서 EAGLE3/DFlash/DSpark 계열 speculative draft
- 모든 draft-model speculator를 위한 adaptive verification
- kernel warmup / graph capture lifecycle 개선
- CUDA Graph capture 중 GC freeze
- non-compiled model의 graph fallback/correctness guard 강화

### CUDA Graph startup

PR #54646은 MRV2 graph capture 중 GC를 freeze한다.

Release note의 H200 사례는 graph capture 약 12s -> 2s, engine init 약 28.9s -> 8.2s 개선을 보고한다.

이 수치는 workload-independent guarantee가 아니지만, **0.30 startup profile이 0.29와도 달라질 수 있는 이유**다.

### Migration rule

다음은 반드시 별도 dimension으로 기록한다.

```text
MRV1/MRV2
EAGER/FULL_DECODE_ONLY/FULL_AND_PIECEWISE
graph capture sizes
post-capture GPU memory
KV cache bytes
startup compile/capture time
```

## 5. Scheduler / prefix cache / hybrid state

v0.30의 H100/H200-class online default는 여전히:

```text
max_num_batched_tokens = 8192
max_num_seqs = 1024
```

이며 >=160 GiB GPU tier에서는 OpenAI API server도 MBT 16384를 기본으로 사용한다.

현재 P/D workload처럼 role-specific tuning을 하는 환경에서는 이 default를 채택하지 말고 계속 explicit pin한다.

### Prefix caching

v0.30 source는 supported model이면 prefix caching을 기본 활성화하는 modern policy를 유지한다.

Hybrid model에서는 다음을 함께 봐야 한다.

- `prefix_cache_retention_interval`
- `mamba_cache_mode`
- `prefix_match_unit`
- replay/checkpoint boundaries
- speculative resume position

### Mamba `all` mode

`mamba_cache_mode=all`은 v0.30에서 deprecated warning 대상이다.

Compatibility/production profile은 가능한 한 `align` 또는 model-supported policy를 기준으로 잡고 `all`을 신규 설정으로 채택하지 않는다.

### Replay/checkpoint fixes

v0.30은:

- EAGLE resend에서 두 replay boundary retention
- align-mode Mamba state lifecycle
- internal prefix checkpoint + partial prefix caching + speculative decoding
- resumed P/D request의 state/padding

경로를 계속 hardening한다.

Hybrid Qwen/Kimi의 TTFT 또는 concurrency가 달라졌다면 kernel 하나만 보지 말고 state/checkpoint policy까지 같이 비교한다.

---

## 6. P/D, DCP, PCP, Mooncake and NIXL

v0.30 large-scale serving은 P/D 자체보다 **parallelism combination**이 더 복잡해졌다.

Relevant additions/fixes:

- symmetric DCP disaggregation for hybrid Mamba models (#55531)
- PCP + DCP on sparse-MLA models
- PCP + single-module MTP / replicated DSpark
- PCP decode-only FULL CUDA Graph (#53867)
- PCP producer shards as NIXL transfer ranks
- Mooncake Store heterogeneous TP sharing (#53129)
- Mooncake heterogeneous PP completion
- Mooncake producer partial Mamba tails
- hybrid-model finish-time saves
- failed remote loads surfaced to scheduler
- NIXL per-region transfer geometry
- NIXL no-eviction-mid-transfer protection
- NIXL full-prefix completion handling

### Important interpretation

```text
same KVTransferConfig JSON
!= same transfer contract
```

0.26 -> 0.30에서 다음이 모두 달라질 수 있다.

```text
cache group geometry
block/page size
prefix match unit
DCP/PCP rank ownership
recurrent state checkpoint
transport dependency
request completion semantics
abort/retry path
```

P/D qualification은 connector startup이 아니라 long-context soak + abort/failure injection까지 포함해야 한다.

---

## 7. Mooncake abort timeout remains operationally relevant

v0.30 source에는:

```text
VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT = 480
```

default가 존재한다.

이 값은 정상-path throughput knob가 아니라 failure cleanup contract로 본다.

특히 malformed/frontend-failed request와 정상 request가 겹치는 상황에서는:

- Decode request admission
- transfer metadata creation
- remote KV wait
- abort propagation
- worker task occupancy
- scheduler state cleanup

을 별도로 계측한다.

Timeout을 줄이는 것만으로 stuck state가 해소된다고 가정하지 않는다.

---

## 8. Collectives and NVLink-less systems

v0.29에서 CUDA TP group의 FlashInfer all-reduce default가 활성화됐고, v0.30 source도:

```text
VLLM_ALLREDUCE_USE_FLASHINFER = True
```

를 유지한다.

v0.30은 추가로 opt-in:

```text
VLLM_ALLREDUCE_USE_FLASHINFER_PCIE_IPC = False
```

backend를 제공한다 (#53576).

### Implication

NVLink가 없는 PCIe-only multi-GPU system에서는 새로운 A/B 후보가 생겼다.

그러나 migration compatibility phase에서는 communicator까지 동시에 바꾸지 않는다.

```text
0.26-compatible collective policy
 -> 0.30 default FlashInfer AR
 -> PCIe IPC backend if topology warrants
```

순서로 분리한다.

---

## 9. Fast Start: new weight lifecycle, not a free startup optimization

v0.30은 per-GPU weight-cache daemon과:

```text
--load-format ipc_cache
```

를 추가한다 (#54921).

Daemon이 post-quantized, TP-sharded weight를 GPU memory에 유지하고 engine restart 시 CUDA IPC로 mapping한다.

추가 지원:

- FP4 checkpoints
- multi-node TP

### Operational trade-off

이 기능을 쓰면 weight lifetime이 engine process lifetime과 분리된다.

따라서 다음 failure domain이 새로 생긴다.

```text
daemon lifecycle
IPC handle lifetime
GPU UUID/socket mapping
daemon-engine version compatibility
cached-weight identity
restart/rollback interaction
```

0.26 -> 0.30 compatibility phase에는 넣지 않고, startup/recovery optimization phase에서 별도 인증한다.

---

## 10. Frontend / scale-out API breaking change

v0.30 breaking change 중 platform 관점에서 가장 직접적인 항목이다.

Plain `vllm serve`의 scale-out endpoint는 이제:

```text
--enable-scale-out
```

을 명시해야 노출된다.

기존:

```text
VLLM_ENABLE_SCALE_OUT_ENDPOINTS
```

방식은 대체됐다.

Relevant endpoints include render/derender와 `/inference/v1/generate` 계열 scale-out path.

### Platform decision

필요한 endpoint만 명시적으로 활성화한다.

```text
ordinary serving endpoint
 -> scale-out disabled

renderer / token-in-token-out / disaggregated frontend path
 -> --enable-scale-out
```

API surface가 줄어드는 변화이므로 startup success만 확인하지 말고 route registration test를 추가한다.

## 11. Responses / parser / observability

v0.30 frontend relevant changes:

- stateless `/v1/responses/render`
- reasoning token usage accounting
- parser plugin loading from site-packages
- structured-output validation hardening
- unsupported Responses input item -> 400
- unsupported `reasoning_effort` -> client error
- Anthropic `stop_sequence` message delta
- Mooncake/NIXL connector metrics in Rust frontend
- `max_num_queued_reqs` shared across API server processes
- request preemption histogram

Responses/Anthropic/platform adapter를 별도로 두는 환경에서는 raw engine output과 protocol response를 각각 regression-test한다.

## 12. Qwen3.8 / Qwen3.5-family

v0.30에는 Qwen3.8-Flash-Next의 sparse indexer, PLE, FP8 cache, UVA offload, MTP path가 크게 발전했다.

하지만 이것을 Qwen3.8-27B hybrid/GDN checkpoint와 같은 architecture로 묶지 않는다.

### Still-open upstream watchlist

v0.30 release 이후에도 다음 PR은 open/unmerged 상태다.

- #54624 Qwen3.5-family calibrated FP8 KV scale loading
- #55294 DFlash2 FP16 speculative decoding
- #55617 hybrid GDN + MTP concurrency

따라서 Qwen3.5/3.6/3.8 family에서:

```text
FP8 KV
MTP
DFlash2
concurrency >= 4
```

를 쓰는 경우 v0.30 startup success만으로 production-ready 판정을 내리지 않는다.

## 13. Kimi K3

v0.30 Kimi K3 relevant changes:

- native CUDA AttnRes on SM100
- KDA mixed-batch gather/scatter removal
- grouped FP8 MLA cache insertion
- overlapped TP8 KDA projections
- FlashInfer KDA kernels
- internal prefix checkpoints + partial prefix caching + speculative decoding
- symmetric DCP disaggregation for hybrid Mamba

K3는:

```text
MRV2
+ recurrent state
+ MLA
+ spec decode
+ DCP
+ parser
+ P/D
```

를 동시에 검증해야 한다.

## 14. DeepSeek V4 / V4.1

v0.30은 DeepSeek-V4.1-Flash를 추가하고 V4 sparse MLA/MoE path를 계속 확장한다.

Relevant:

- V4.1 whole-KV MXFP8 on SM100
- Mega-mHC
- async Engram prefetch / DP sharding
- V4 `kv-cache-dtype auto` -> `fp8_ds_mla` path
- sparse prefill/indexer fixes
- MegaMoE startup/fallback fixes
- HiSparse host-resident sparse-MLA tier

따라서 V4 계열은 model revision까지 certification tuple에 포함한다.

---

## 15. GLM 5.x

v0.30은 GLM-5.3-Flash support와 EPLB, KDA prefill, sparse/dense prefill path를 추가한다.

GLM 계열은 계속:

```text
raw engine token correctness
vs
parser/template correctness
```

를 분리한다.

Sparse-attention backend capability와 model wrapper capability를 동일시하지 않는다.

---

## 16. Breaking / deprecation checklist

v0.30에서 migration manifest에 반영할 항목:

- **ADD when needed**: `--enable-scale-out`
- **REMOVE**: `VLLM_ENABLE_SCALE_OUT_ENDPOINTS`
- **REMOVE**: deprecated `VLLM_PREFIX_CACHE_RETENTION_INTERVAL` env
- **REMOVE**: deprecated `VLLM_MM_HASHER_ALGORITHM` env
- **AVOID**: `mamba_cache_mode=all` 신규 채택
- **MIGRATE**: `python -m vllm.entrypoints.grpc_server` -> `vllm serve --grpc`
- **RETEST**: vendor YaRN aliases / max-model-len behavior
- **RETEST**: GPTQ checkpoints relying on removed activation-ordering `g_idx`

## 18. Post-tag watchlist

### OPEN / not fixed in v0.30

- #54624 Qwen3.5-family FP8 KV scale loading
- #55294 DFlash2 FP16 speculative decoding
- #55617 hybrid GDN + MTP concurrency
- #58158 source-build dependency/toolchain floor: issue reporter는 v0.30 pinned dependency 일부가 C++20 `std::format`을 사용해 문서상 GCC >=11.3보다 높은 실질 compiler floor를 요구할 수 있다고 보고함. source build/폐쇄망 image에서는 별도 검증

이 항목들은 v0.30 기능으로 기록하지 않고 **open upstream risk**로 유지한다.

## 19. Candidate assessment

0.30은 0.29보다 변경량이 더 많지만, 0.29에서 뒤집힌 MRV2/hybrid/P-D path가 추가 hardening된 시점이기도 하다.

따라서 각 intermediate version을 production certify하기보다:

```text
0.26 operational baseline
  -> 0.30-cu129 compatibility candidate
      -> failure 시 0.27 / 0.28 / 0.29 source/binary bisect
      -> 0.30 CUDA 13 optimization candidate
```

전략이 효율적이다.

단, 현재 P/D + long-context + hybrid-state workload에서는 **Mooncake/NIXL dependency와 failure cleanup을 engine correctness와 동급의 P0 gate**로 둔다.
