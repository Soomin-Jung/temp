# vLLM v0.26.0 Source Audit

Release: 2026-07-27  
Upstream: https://github.com/vllm-project/vllm/releases/tag/v0.26.0

## 1. Executive assessment

v0.26.0은 현재 migration 분석의 **operational baseline**이다.

이 tag에서 이미 modern vLLM의 핵심 구조 대부분이 존재한다.

- V1 engine + MRV1/MRV2 coexistence
- hybrid KV cache groups
- Mamba/GDN state cache
- prefix caching
- speculative decoding
- NIXL/Mooncake KV connectors
- P/D disaggregation
- Python/Rust frontend 동시 발전
- Streaming Parser Engine rollout

따라서 0.29로의 migration은 legacy engine에서 modern engine으로 가는 migration이 아니다. **이미 modern feature를 쓰고 있는 0.26 execution contract를, 0.29에서 기본값과 지원 범위가 크게 확장된 execution contract로 옮기는 작업**이다.

## 2. Baseline dependency contract

`requirements/kv_connectors.txt` at v0.26.0:

```text
lmcache >= 0.3.9
cupy-cuda13x < 14.1.0
nixl == 1.3.1
mooncake-transfer-engine >= 0.3.8
```

중요: upstream requirement는 범위이고, 실제 운영 검증 package는 별도 pin해야 한다.

기존 same-node P/D validation에서는 Mooncake `0.3.10.post2`를 source-build해 `USE_INTRA_NVLINK=ON`을 확보한 profile을 사용했다. 이것은 vLLM v0.26의 `>=0.3.8` dependency와 모순되지 않지만, **upstream vLLM version만 pin해서는 transport feature set을 재현할 수 없다는 증거**다.

## 3. Cache / hybrid baseline

v0.26 `CacheConfig`에 이미 다음 surface가 있다.

- `enable_prefix_caching=True`
- `prefix_match_unit`
- `mamba_block_size`
- `mamba_cache_dtype`
- `mamba_ssm_cache_dtype`
- `mamba_cache_mode`
- `kv_cache_memory_bytes`
- `kv_cache_dtype_skip_layers`
- group-aware `kv_cache_size_tokens`

### 3.1 `mamba_cache_mode`

v0.26 source의 설명:

- `none`: prefix caching off
- `all`: block boundary마다 Mamba state cache; 지원 모델에서 prefix caching enabled 시 default behavior
- `align`: scheduler step의 마지막 token 및 block boundary에 state cache

이 semantics는 v0.28/0.29에서 바뀐다. 특히 0.28에서는 `align`이 prefix caching enabled의 default로 명시되고, 0.29에서는 retention/checkpoint policy가 별도 CLI로 분리된다.

따라서 hybrid 모델의 0.26 vs 0.29 memory/TTFT 비교는 `enable_prefix_caching` boolean 하나로 재현할 수 없다.

### 3.2 KV memory isolation

`kv_cache_memory_bytes`는 v0.26에도 존재한다.

Migration A/B에서 이 옵션을 이용하면:

```text
0.26 automatic profile
0.29 automatic profile
```

차이와

```text
same fixed KV bytes + different runner/runtime
```

차이를 분리할 수 있다.

이는 long-context prefill의 non-KV headroom OOM을 분석할 때 유용하다.

## 4. Mamba backend baseline

v0.26 `MambaConfig`:

- default backend: `TRITON`
- alternate: `FLASHINFER`
- stochastic rounding support
- Triton stochastic rounding은 data-center Blackwell capability family 100 요구

아직 v0.28의 `CPU` backend와 `mamba_ssu_algorithm` selector는 없다.

## 5. KVTransferConfig baseline

v0.26 top-level `KVTransferConfig`는 이미 현재와 거의 같은 core contract를 가진다.

```text
kv_connector
engine_id
kv_buffer_device
kv_buffer_size
kv_role = kv_producer | kv_consumer | kv_both
kv_rank
kv_parallel_size
kv_ip / kv_port
kv_connector_extra_config
kv_connector_module_path
kv_load_failure_policy = fail | recompute
```

중요한 관찰:

**0.26 -> 0.29의 KV migration은 top-level JSON schema가 통째로 바뀌는 migration이 아니다.**

실제 변화는:

- connector implementation
- cache-group layout
- request/scheduler metadata
- async lookup/load timing
- P/D push/pull semantics
- DCP/PCP support
- Mamba/SSM transferable state
- connector compatibility hash

에 집중되어 있다.

따라서 Helm values의 `kvTransferConfig` JSON이 그대로 parse된다고 해서 migration compatibility가 확보됐다고 보면 안 된다.

## 6. P/D / distributed changes

v0.26 release에서 중요한 항목:

- hybrid attention DCP: #40996
- DCP + EAGLE for MLA backend: #48180
- NIXL pipeline-parallel prefill push mode: #45880
- encoder-cache transfer params: #42433
- CPU-offloading encoder cache connector: #47423

이 release는 P/D가 1P1D 단순 KV copy를 넘어 PP/DCP와 결합하는 방향을 보여준다.

## 7. Frontend / API

Relevant changes:

- Rust frontend video/audio support
- Seed-OSS tool parser
- `continue_final_message` + renderer sentinel
- `/v1/completions` bad_words
- Python OpenAI endpoint logprob token IDs
- `include_reasoning` for non-Harmony models
- endpoint plugin framework
- grammar compilation failure가 engine crash로 전파되지 않도록 개선

현재 baseline validation에서는 frontend를 engine과 같이 pin해야 한다.

특히 parser model test는 다음을 기록한다.

- chat template hash
- tokenizer revision/hash
- reasoning parser name
- tool parser name
- stream/non-stream mode
- reasoning include/exclude option
- final finish reason / tool-call structure

## 8. DeepSeek V4 relevance

v0.26은 DSV4 serving이 빠르게 최적화되는 구간이다.

이후 0.27~0.29에서 sequence parallel, sparse MLA, DSpark, DCP/PCP, graph range, shared expert fusion 등이 계속 바뀌므로 **0.26의 DSV4 benchmark를 0.29와 단순 throughput 비교하면 변경 변수가 너무 많다.**

DSV4 migration은 최소 다음 축으로 분리한다.

1. plain decode
2. MTP
3. DSpark
4. P/D
5. TP/DP/EP
6. CUDA Graph mode
7. MLA/sparse MLA backend

## 9. Current baseline deployment knobs

0.26 기반 운영/실험에서 주로 명시적으로 관리하는 surface:

```text
max-model-len
gpu-memory-utilization
kv-cache-dtype
block-size
max-num-batched-tokens
max-num-seqs
enable/no-enable-chunked-prefill
compilation-config / cudagraph mode
speculative-config
TP / DP / EP
reasoning-parser
tool-call-parser
enable-auto-tool-choice
renderer-num-workers
safetensors-load-strategy
FlashInfer autotune policy
KV transfer config
```

Migration 원칙은 이 값을 0.29 default로 풀어버리는 것이 아니라 **먼저 0.26 semantics와 최대한 동일하게 명시해 candidate를 만들고, 이후 0.29 optimization을 한 축씩 enable**하는 것이다.

## 11. Baseline definition

0.26 baseline을 보존할 때 Docker image tag만 남기지 않는다.

필수 reproducibility set:

- image digest
- vLLM git SHA
- CUDA flavor (`cu129` 등)
- NVIDIA driver
- Torch / Triton / FlashInfer / Transformers
- NIXL exact version
- Mooncake exact version + wheel SHA 또는 CMake flags
- model/tokenizer revision
- full argv
- env vars
- parser config
- graph mode
- topology / TP-DP-EP
- P/D role와 connector config

이 전체가 migration baseline이다.
