# vLLM v0.24.0 Source Audit

Release: 2026-06-29  
Upstream: https://github.com/vllm-project/vllm/releases/tag/v0.24.0

## 1. Executive assessment

v0.24.0은 현재 기준에서 오래된 release지만, E2E serving platform 관점에서는 중요한 경계다.

- Python frontend의 model-specific parser들을 하나씩 손대는 구조에서 **stateful Streaming Parser Engine**으로 가는 전환이 시작됐다.
- tool calling과 Responses API의 strict-mode semantics가 강화됐다.
- Rust frontend가 auth/CORS/tokenize/abort/pause 등 control/API surface를 빠르게 확장했다.
- KV connector/P-D 영역에서는 NIXL push와 Mooncake PP/async lookup이 들어오면서 connector가 단순 point-to-point 전송이 아니라 scheduler/cache layout과 강하게 결합되기 시작했다.
- DeepSeek V4와 hybrid MLA/SWA 같은 모델 특화 cache region을 connector가 이해해야 하는 문제가 이미 드러났다.

현재 v0.26+ 운영을 이해할 때 v0.24를 봐야 하는 이유는 parser와 disaggregation이 이 시기부터 **독립 기능이 아니라 serving execution path의 일부**가 되었기 때문이다.

## 2. Frontend / parser

### 2.1 Streaming Parser Engine

PR #45413은 `vllm/parser/engine/` 아래에 다음 pipeline을 추가했다.

```text
(delta_text, delta_token_ids)
  -> TokenIDScanner
  -> IncrementalLexer
  -> Parser state machine
  -> SemanticEvent stream
```

핵심 파일:

- `vllm/parser/engine/streaming_parser_engine.py`
- `incremental_lexer.py`
- `token_id_scanner.py`
- `parser_engine_config.py`
- `events.py`

중요한 설계 변화는 parser가 단순 regex/post-processing이 아니라 **request-local state machine**이 되었다는 점이다.

`StreamingParserEngine`은 request마다 state를 유지하면서 reasoning/content/tool-name/tool-args state를 넘나든다. tool argument JSON은 stream 중 닫는 brace를 바로 emit하지 않고 safe watermark까지 buffer하는 로직을 가진다. 따라서 parser compatibility 검증은 최종 문자열만 비교하면 부족하다.

필수 regression corpus:

1. `stream=false` complete response
2. `stream=true`, token delta와 text delta가 같이 오는 경우
3. special token이 text fragment 경계를 가르는 경우
4. reasoning end와 tool start가 같은/인접 chunk에 오는 경우
5. tool arguments가 여러 SSE delta에 나뉘는 경우
6. parallel tool calls
7. `enable_thinking=true/false`
8. stop token 직전/직후 parser state

### 2.2 GLM 4.7/5.1/5.2 parser

PR #45915는 Streaming Parser Engine을 기반으로 GLM 4.7/5.1/5.2 parser를 추가했다.

PR 설명상 다음 조합을 직접 검증했다.

- thinking on/off
- streaming on/off

GLM 5.x를 주요 serving target으로 잡는 platform에서는 parser를 단순 CLI 이름 존재 여부로 검증하지 말고, **model chat template + tokenizer special token + streaming parser adapter** 조합으로 version pin해야 한다.

### 2.3 Tool calling / Responses

release에서 중요한 frontend 변화:

- Chat Completions strict tool calling: #45003
- Responses API strict mode: #45396
- parser consolidation in chat serving: #45548
- Responses streaming function-call ID fix: #44608
- Harmony streaming/non-streaming path refactor: #45171, #45104
- Anthropic Messages cache usage / system message / tool-use correctness fixes

즉 v0.24부터 `/v1/chat/completions`, `/v1/responses`, `/v1/messages`를 같은 모델에 연결할 때 **frontend adapter별 parsing semantics**를 별도 테스트해야 한다.

### 2.4 Rust frontend

이 release에서 Rust frontend는 다음 surface를 빠르게 확보한다.

- API key auth
- CORS
- `/tokenize`, `/detokenize`
- pause/resume/is_paused
- abort requests
- world size query
- thinking token budget
- `parallel_tool_calls=false`
- continuous usage stats
- `/v1/models` metadata
- Python tool-parser bridge
- dedicated HTTP/ZMQ runtime

이 시점에는 Rust frontend가 Python frontend를 완전히 대체한다고 보면 안 된다. 오히려 **renderer/parser/control plane을 분리해 옮겨가는 transition period**로 보는 것이 안전하다.

## 3. KV transfer / P-D

release의 relevant PR:

- #35264: NIXL prefill -> decode KV push
- #44583: mixed full-attention + MLA group의 per-region KV transfer classification
- #44528: Mooncake pipeline-parallel P/D
- #45659: Mooncake async lookup
- #45969: compact chunk hash / zero-copy lookup
- #45444: Mooncake SWA block skipping
- #46628: DP supervisor + P/D fixes
- #45831: DeepSeek V4 disaggregation fix
- #44854: `P2pNcclConnector` 제거

### DSV4 fix가 주는 교훈

PR #45831의 문제는 `base_worker.py`가 MLA region 판별 시 `MLAAttentionSpec`만 인식하고, DSV4 compressor layer의 `SlidingWindowMLASpec`을 누락한 것이었다.

결과적으로 모델이 'MLA 계열'이라는 고수준 분류만 맞아서는 충분하지 않다.

```text
model architecture
 -> KV cache group/spec type
 -> connector-transferable region classification
 -> block layout
 -> producer/consumer metadata
```

이 전체가 호환돼야 P/D가 동작한다.

따라서 신규 모델 P/D 검증은 반드시 layer/spec introspection을 포함해야 한다.

## 4. Parser/connector observability

v0.24에는 `vllm:tool_call_parser_invocations_total` metric이 추가됐다. 또한 cache capacity metric이 group-aware semantics를 반영하기 시작한다.

Platform 레벨에서는 다음을 분리해서 관측하는 방향이 맞다.

- frontend parse errors
- tool parser invocation / fallback
- reasoning parser boundary errors
- KV lookup hit/miss
- external KV load/save latency
- transfer failure -> recompute/fail
- per-KV-group capacity

## 5. Migration significance

### v0.24에서 반드시 보존해야 할 정신 모델

1. parser는 request-local state machine이다.
2. streaming correctness는 non-streaming correctness와 별도 문제다.
3. KV connector는 model layer/cache spec을 이해한다.
4. P/D support는 `connector supports model X` 한 문장으로 판단할 수 없다.
5. frontend와 engine을 독립 버전처럼 테스트해야 한다.

## 7. Platform action

현재 0.26→0.29 migration에서는 v0.24 자체를 deploy candidate로 볼 필요는 없다. 대신 다음 regression suite의 historical baseline으로 사용한다.

- parser event replay
- GLM thinking/tool stream
- DSV4 hybrid MLA/SWA transfer classification
- NIXL push lifecycle
- Mooncake async lookup semantics
