# vLLM v0.29.0 Source Audit

Release: 2026-09-09  
Upstream: https://github.com/vllm-project/vllm/releases/tag/v0.29.0

## 1. Executive assessment

v0.29.0은 0.26 baseline에서 볼 때 단순 feature accumulation이 아니라 **execution-path default inversion**이 일어난 release다.

핵심:

- Model Runner V2가 모든 모델의 default가 됨
- MRV2 CUDA Graph memory profiling을 KV cache auto-sizing에 반영
- Mamba/Sliding Window prefix-cache checkpoint retention policy 분리
- FlashInfer all-reduce가 TP CUDA group에서 default-on
- queue admission control 추가
- parser engine adapter 통합 지속
- Mooncake/NIXL hybrid/Mamba/DCP path 강화
- Qwen3.8-Flash-Next 추가
- Kimi K3/DSV4/GLM5.x kernel/DCP/spec decode 개선

따라서 0.26과 같은 argv를 그대로 넣어도 **runner, communicator, cache checkpoint policy, graph reservation, scheduler path**가 달라질 수 있다.

## 2. Model Runner V2: default policy inversion

PR #53183은 이전의 `DEFAULT_V2_MODEL_RUNNER_ARCHITECTURES` 중심 selection을 제거한다.

v0.25 계열:

```text
model qualifies for V2? -> yes: V2 / no: V1
```

v0.29:

```text
V2 by default
 -> platform/model exception?
 -> V2 unsupported feature?
```

으로 사고방식이 바뀐다.

### 2.1 Actual PR semantics

PR patch에서:

- architecture whitelist 제거
- hybrid/attention-free default-V1 branch 제거
- PCP/DSpark/DFlash2 등을 V2로 force하던 special-case가 사라짐: 이제 default가 V2라서 필요 없음
- V1을 명시적으로 선택했을 때 `V1 unsupported feature` validation 추가
- ROCm에서는 DeepSeek V3.2 / V4를 default V1 architecture로 유지

따라서 `MRV2 default for all models`를 **MRV1 code removal**로 읽으면 안 된다.

V1은 여전히:

- explicit override
- ROCm exception
- MRV2 unsupported feature fallback/validation

관점에서 존재한다.

### 2.2 Migration implication

0.26에서 hybrid Qwen/Kimi를 V1 path로 타던 경우 0.29에서 같은 model/config가 MRV2로 바뀔 수 있다.

따라서 다음을 반드시 기록한다.

- resolved `use_v2_model_runner`
- runner-specific worker/model-runner class
- CUDA Graph manager
- KV cache layout
- Mamba metadata preparation
- speculator type

Benchmark 이름에 `vllm=0.29`만 적지 말고 `MRV1/MRV2`를 별도 dimension으로 남긴다.

## 3. MRV2 CUDA Graph memory profiling

PR #53306은 MRV2 `profile_cudagraph_memory()`를 실제 구현한다.

변경된 path:

- `vllm/v1/worker/gpu/cudagraph_utils.py`
- `vllm/v1/worker/gpu/model_runner.py`
- Mamba/GDN/short-conv layers

Profiling 시:

- temporary KV cache config를 초기화하고
- KV connector는 NO-OP으로 대체하며
- Mamba layer는 cheap warmup path를 사용하고
- attention metadata/kernel은 profiling에 필요한 형태로 준비한다.

이 결과가 KV cache auto-sizing의 memory budget에 반영된다.

### Why it matters

0.26과 0.29에서 같은:

```text
gpu_memory_utilization = 0.94
```

를 줘도 available KV bytes가 동일하다고 가정할 수 없다.

0.29의 accounting은 CUDA Graph reservation을 더 명시적으로 고려한다.

따라서 migration memory test를 두 단계로 수행한다.

1. **automatic memory policy comparison**
2. `kv_cache_memory_bytes`로 KV를 고정한 execution-path comparison

이렇게 해야 graph memory accounting 변화와 model/kernel workspace 변화를 분리할 수 있다.

## 4. FlashInfer all-reduce default

PR #52998:

```python
VLLM_ALLREDUCE_USE_FLASHINFER: False -> True
```

그리고 CUDA communicator에서 batch-invariant mode가 아닐 때 FlashInfer all-reduce를 사용할 수 있게 한다.

Release note도 TP CUDA group의 default-on으로 명시한다.

### Impact

TP2/TP4/TP8에서 communicator backend가 migration 변수다.

검증 matrix:

```text
0.26 baseline
0.29 + VLLM_ALLREDUCE_USE_FLASHINFER=0
0.29 + default FlashInfer allreduce
```

특히 다음 모델에서 확인한다.

- Qwen3.5/3.6/3.8
- Kimi K3
- DSV4
- GLM 5.x

Correctness corpus도 필요하다. v0.25.1에서 mixed-dtype RMSNorm fusion silent corruption이 실제로 있었기 때문이다.

## 5. Mamba / Sliding Window prefix cache retention

PR #52216은 `CacheConfig.prefix_cache_retention_interval`을 추가한다.

Default:

```text
0
```

Semantics:

- `0`: semantic checkpoints만 retain
  - latest replay boundary
  - shared-prefix junction 등
- positive N: semantic checkpoint + N-token periodic checkpoint
- `None`: dense checkpoint retention

적용 대상은 sliding-window와 Mamba cache group이다.

### 5.1 Why this is not just a memory knob

Mamba/SSM state는 attention KV처럼 임의 token boundary의 state를 바로 복원할 수 있는 구조가 아니다. replay/checkpoint semantics가 필요하다.

따라서 retention interval은:

- prefix-cache hit granularity
- replay work
- TTFT
- state-cache memory
- external KV transfer

를 동시에 바꾼다.

### 5.2 Spec decode interaction

Release는 EAGLE/MTP hybrid model에서 dense retention이 자동 복원되는 path도 포함한다 (#55760, #55861).

즉 `prefix_cache_retention_interval=0`이라고 적힌 CLI 값만 보고 effective checkpoint density를 단정하면 안 된다.

resolved cache configuration과 model/spec method를 함께 본다.

### 5.3 Internal prefill checkpoint

PR #52789은 Mamba internal prefill checkpoint로 TTFT를 개선한다. Release note 기준 9~25% 개선 사례가 보고됐다.

0.26→0.29 hybrid benchmark에서 TTFT가 좋아졌다면 kernel 성능뿐 아니라 checkpoint/reuse policy 차이인지 구분해야 한다.

## 6. CacheConfig evolution

v0.29 `CacheConfig`에는 0.26 대비 다음 surface/semantics가 추가 또는 명확화된다.

- resolved `KVCacheLayout`
- `prefix_cache_retention_interval`
- ReplaySSM
- `use_kda_recoverssm`
- `nvfp4_4over6`
- richer KV capacity semantics

`prefix_cache_retention_interval`은 config compute hash에서는 제외된다. 즉 compiled graph identity를 바꾸는 knob라기보다 runtime cache policy로 취급된다.

## 7. KVTransferConfig: schema stability vs implementation change

v0.26과 v0.29의 top-level `KVTransferConfig` field는 놀랄 만큼 비슷하다.

v0.29에는 `has_connector()` helper가 추가돼 `MultiConnector` child까지 검사한다.

이 사실은 중요한 결론을 준다.

> migration risk는 JSON schema rename보다 connector lifecycle/cache layout/request metadata에 있다.

따라서 Helm config parse 성공을 compatibility test로 간주하지 않는다.

## 8. KV connector / disaggregation

- Mooncake hybrid DCP prefix caching: #53324
- externally-transferable KV cache group identification: #53779
- async KV load를 forward launch 뒤로 defer: #53333
- `/inference/v1/generate`에 `kv_transfer_params`: #42644
- Mamba/Mooncake fixes: #51362, #51358, #53663
- Mamba/NIXL fix: #53523
- NIXL P/D DCP for MLA: #50611

### Platform implication

Connector contract를 다음 세 층으로 본다.

```text
Control/config
  KVTransferConfig + router metadata

Scheduler/cache metadata
  block hashes, cache groups, DCP/PCP, Mamba checkpoints

Data transport
  Mooncake/NIXL protocol and memory registration
```

세 층 중 하나라도 mismatch면 P/D가 깨질 수 있다.

## 9. Queue admission control

v0.29에:

- `--max-num-queued-reqs`
- `--max-num-queued-tokens`

가 추가된다 (#49445).

`max_num_queued_tokens`는 long-context prefill queue를 보호하는 local safety valve로 특히 의미가 있다.

다만 E2E platform에 이미 API gateway/router/load balancer가 있는 경우 double queueing이 생길 수 있다.

정책 ownership을 명시한다.

```text
Gateway: client fairness / rate limit
Router: model/replica/P-D routing
vLLM admission: engine-local overload guard
```

vLLM admission은 마지막 방어선으로 두는 것이 자연스럽다.

- `kimi_k3`
- `ling3`
- `hy_v4`
- `muse_glimmer`

Qwen/DSV4/GLM parser는 기존 이름이 존재한다고 끝이 아니다. template/tokenizer/adapter implementation이 계속 바뀐다.

## 11. Qwen3.8-Flash-Next

PR #53896이 Qwen3.8-Flash-Next를 추가한다.

Upstream PR validation:

- BF16 / FP8 / NVFP4
- GB300 / GB200 / H200
- MI355X BF16
- TP2 / TP4 / TEP4
- MTP example: 3 speculative tokens

Example:

```bash
vllm serve Qwen/Qwen3.8-Flash-Next \
  -tp 4 \
  --enable-prefix-caching \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
```

이 PR이 중요한 이유는 Qwen3.8을 단순 Qwen3.6-compatible checkpoint로 보는 것이 아니라 **새 architecture/weight format/spec path를 독립 검증**해야 함을 보여주기 때문이다.

## 12. Kimi K3

v0.29 release:

- NVFP4 checkpoint support
- fused MXFP4 top-k finalization
- Mamba metadata preparation single Triton launch
- Hopper/SM100 low-latency GEMM tuning
- GEMM-RS -> GEMM-AR
- MLA gate fusion
- DCP + DSpark
- DCP partial prefix-cache hit

K3는 MRV2, Mamba state, parser, spec decode, DCP가 모두 동시에 움직이는 모델이므로 **model-specific lane가 필수**다.

## 13. DeepSeek V4

Relevant:

- shared expert -> MegaMoE fusion
- adaptive top-k
- sparse MLA spec decode on SM90
- stable mHC buffers across weight sync
- opt-in FlashInfer `moe_ep`

DSV4는 architecture-specific breakable CUDA Graph set에도 포함되는 계열이므로 compilation config를 일반 dense model과 공유하지 않는 것이 안전하다.

## 14. GLM 5.x

Relevant:

- GLM-5.2 dense MHA path correction
- sparse MLA verification on SM100
- DCP query replication option `--dcp-q-replicate`
- DCP fused attention fixes
- masked MHA prefill / sparse MLA kernel changes
- frontend template parity

GLM은 parser와 sparse attention execution을 독립 gate로 본다.

## 15. Deprecations / breaking

- `python -m vllm.entrypoints.openai.api_server` deprecated
- `vllm serve`가 canonical entrypoint
- 10 deprecated model architectures removed
- PyAV video decoder backend removed

Custom image/entrypoint에서 module 직접 실행을 사용한다면 migration 대상이다.

## 18. Candidate status

v0.29.0은 0.26 이후 intermediate release를 각각 production certify하기보다 **차기 candidate baseline으로 직접 평가할 가치가 충분한 release**다.

단, candidate certification은 version bump test가 아니라 MRV2/frontend/parser/hybrid cache/connector/communicator를 각각 분리한 migration program으로 수행해야 한다.
