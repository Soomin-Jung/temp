# vLLM v0.26.0 -> v0.30.0 Migration Program

업데이트: 2026-09-29 KST

## 1. Purpose

현재 production baseline인 v0.26.0에서 v0.30.0으로 이동할 때 필요한 **E2E compatibility, performance, dependency, rollout program**을 정의한다.

이 migration의 unit은 vLLM package가 아니다.

```text
Client
 -> API Gateway / proxy
 -> protocol adapter
 -> vLLM frontend / renderer / parser
 -> Scheduler
 -> Model Runner
 -> model-specific kernels / speculator
 -> KV / recurrent-state cache
 -> KV transfer connector
 -> TP / DP / EP / DCP / PCP
 -> CUDA / Torch / Triton / FlashInfer / NCCL
 -> GPU / NIC topology
```

따라서 완료 조건은 `v0.30 starts`가 아니라 **0.26에서 통제하던 serving contract를 0.30에서도 설명 가능하게 재현하고, 새 최적화를 분리해서 채택하는 것**이다.

---

## 2. Why target 0.30 directly

Intermediate release를 각각 production certify하지 않는다.

```text
0.26 operational baseline
   |
   +--> 0.30-cu129 compatibility candidate
          |
          +--> failure 발생 시
               0.27 / 0.28 / 0.29로 source/binary bisect
          |
          +--> 0.30 CUDA13 optimization candidate
```

이유:

- 0.29에서 MRV2 default inversion이 완료됨
- 0.30에서 MRV2/graph/hybrid/P-D path가 추가 hardening됨
- 0.30에서 connector/runtime dependency boundary가 다시 바뀜
- 매 minor release를 production-grade로 인증하면 release cadence를 따라갈 수 없음

버전별 provenance는 `../versions/`에 보존하고, production qualification target만 최신 candidate에 집중한다.

## 3. Migration-critical deltas

### 3.1 Runtime artifact

```text
v0.30.0             -> default CUDA 13.0
v0.30.0-cu129       -> CUDA 12.9
```

첫 candidate는 **cu129**로 잡는다.

목적은:

```text
vLLM semantic delta
vs
CUDA major / kernel dependency delta
```

를 분리하는 것이다.

### 3.2 MRV

```text
0.26: model/feature-dependent V1/V2
0.29+: V2 default
0.30: V2 production path 확대/hardening
```

같은 argv라도 runner, CUDA Graph manager, cache preparation, speculative path가 달라질 수 있다.

### 3.3 KV connector dependencies

v0.30:

```text
NIXL == 1.4.1
Mooncake >= 0.3.12
CUDA13 image -> mooncake-transfer-engine-cuda13 variant
```

Production에서는 Mooncake도 exact pin한다.

### 3.4 Hybrid state / prefix cache

Qwen3.5+/Kimi K3 계열은:

```text
attention KV
+ recurrent GDN/Mamba/KDA state
+ checkpoint/replay boundary
+ speculative resume state
```

를 함께 가진다.

0.30은 이 lifecycle을 상당히 바꿨으므로 cache capacity/TTFT/P-D behavior를 0.26과 직접 동일시하지 않는다.

### 3.5 Frontend endpoint exposure

Scale-out endpoint가 plain `vllm serve`에서 opt-in:

```text
--enable-scale-out
```

으로 바뀌었다.

기존 env 기반 gate를 제거하고 route-registration regression test를 추가한다.

### 3.6 Communicator

FlashInfer all-reduce default-on을 유지하고 PCIe IPC backend가 opt-in으로 추가됐다.

TP benchmark에서는 communicator backend를 명시적으로 기록한다.

## 8. Phase 4 — Scheduler and memory

Compatibility phase에서는 기존 explicit profile을 그대로 가져온다.

예:


### Long-context prefill

Version migration과 scheduling experiment를 섞지 않는다.

먼저 기존:

```text
128K MBT + chunked prefill
```

같은 certified baseline을 재현한다.

그 다음:

```text
higher MBT
no-chunked-prefill
different max-num-seqs
```

를 별도 A/B한다.

### Memory isolation

1. auto KV sizing
2. `kv_cache_memory_bytes` 고정

두 번 비교하여 graph/profile accounting 변화와 kernel workspace 변화를 분리한다.


## 19. Rollout gate

```text
CI image/build
 -> offline correctness
 -> benchmark
 -> isolated namespace
 -> long soak
 -> failure injection
 -> shadow/low-risk endpoint
 -> limited replicas
 -> production canary
 -> broader rollout
```

Go criteria:

- no unknown default drift
- OOM/headroom budget understood

## 20. Rollback unit

Rollback은 vLLM tag 하나가 아니다.

```text
image digest
+ CUDA runtime
+ dependency lock
+ model revision
+ tokenizer/template
+ parser config
+ connector artifact
+ engine config
+ deployment profile
```

을 하나의 release bundle로 취급한다.

Mooncake/NIXL만 0.30 artifact로 남기고 vLLM만 0.26으로 되돌리는 식의 partial rollback은 baseline 재현이 아니다.

---

## 21. Decision

현재 0.26을 유지하면서 0.27/0.28/0.29를 각각 production certify하는 것은 비용 대비 효율이 낮다.

**0.30-cu129를 직접 compatibility candidate로 올리고, 문제가 생길 때 intermediate release를 bisect point로 쓰는 전략**이 합리적이다.

다만 현재 serving 특성상 가장 먼저 통과해야 하는 gate는:

```text
1. long-context memory/scheduler
2. Qwen hybrid state correctness
3. Mooncake/NIXL P/D failure cleanup
4. parser/API correctness
5. TP collective correctness
```

다섯 축이다.
