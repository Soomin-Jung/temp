# vLLM v0.26.0 -> v0.29.0 Migration Program

업데이트: 2026-09-10 KST

## 1. Purpose

이 문서는 vLLM v0.26.0 기반 serving baseline을 v0.29.0 candidate로 이동할 때 필요한 **E2E compatibility, performance, rollout program**을 정의한다.

대상은 단일 `vllm serve` 프로세스가 아니다.

```text
Client
 -> API Gateway / ingress
 -> platform proxy / logging / auth
 -> API router
 -> vLLM frontend / renderer / parser
 -> Scheduler
 -> Model Runner
 -> model-specific kernels / speculator
 -> KV/state cache
 -> KV transfer connector (P/D)
 -> TP/DP/EP communicators
 -> GPU / CUDA / NCCL
```

따라서 migration은 image tag 교체가 아니라 **serving contract 재인증**이다.

---

## 2. Baseline assumptions

v0.26 계열에서 실제 운영/실험은 다음 knob를 적극적으로 explicit tuning한다.

- long `max-model-len` (200K/256K class)
- `gpu-memory-utilization` 0.9x
- FP8 KV cache
- role-specific `max-num-batched-tokens`
- role-specific `max-num-seqs`
- `block-size=256` 계열
- chunked prefill on/off experiments
- CUDA Graph `FULL_DECODE_ONLY`, `FULL_AND_PIECEWISE`
- MTP / DSpark / EAGLE speculative decoding
- TP / DP / EP
- reasoning/tool parsers and auto tool choice
- renderer workers
- Mooncake/NIXL P/D

따라서 default drift보다 더 중요한 것은 **동일 explicit option이 가리키는 내부 implementation path drift**다.

---

## 3. Why direct 0.26 -> 0.29 is acceptable

0.27/0.28을 각각 production certify할 필요는 없다.

권장 전략:

```text
0.26 operational baseline
   |
   +--> 0.29 compatibility candidate
          |
          +--> failure 발생 시 0.27 / 0.28로 source/binary bisect
```

이유:

- 0.29가 MRV2 rollout을 완성한 시점이다.
- 0.28의 여러 intermediate default가 0.29에서 다시 정교화됐다.
- 각 중간 release를 production-grade로 검증하면 validation cost가 release cadence를 따라잡지 못한다.

다만 feature provenance와 regression root cause 분석을 위해 `versions/`에는 모든 intermediate release를 보존한다.

## 4. Major semantic deltas

### 4.1 MRV selection

```text
0.26: architecture/feature dependent MRV1/MRV2
0.29: MRV2 by default; V1 is exception/unsupported lane
```

이 변화 하나만으로:

- worker/model runner
- graph manager
- sampling
- Mamba metadata
- speculative proposer
- memory profiling

이 달라질 수 있다.

### 4.2 CUDA Graph memory accounting

0.29 MRV2는 CUDA Graph memory를 profiling해 KV auto-sizing에 반영한다.

따라서 같은 `gpu-memory-utilization`에서:

```text
available KV bytes(0.26) != available KV bytes(0.29)
```

일 수 있다.

### 4.3 Communicator default

0.29: FlashInfer all-reduce default-on for TP CUDA groups unless excluded by runtime policy.

TP-heavy production에서는 이것이 hidden variable이다.

### 4.4 Hybrid cache policy

0.28~0.29:

- Mamba prefix caching path 강화
- `align` checkpoint semantics
- ReplaySSM
- v0.29 retention interval
- internal prefill checkpoint
- EAGLE/MTP interaction

Qwen3.5+/Kimi 계열의 cache/state behavior가 0.26과 같다고 볼 수 없다.

### 4.5 KV transfer

Top-level `KVTransferConfig`는 거의 동일하지만:

- hybrid cache group
- DCP/PCP
- Mamba state
- async load
- transfer-mode compatibility
- Mooncake Store

가 바뀐다.

`config parsed`는 `connector compatible`이 아니다.

### 4.6 Frontend/parser

Streaming Parser Engine은 0.24부터 시작했지만 0.29까지 adapter, model parser, reasoning boundaries, SSE/render path가 지속적으로 바뀐다.

Parser version은 model engine version만큼 중요한 compatibility dimension이다.

## 5. Migration phases

## Phase 0 — Evidence freeze

0.26 production/benchmark baseline을 재현 가능한 형태로 freeze한다.

필수:

```text
container image digest
vLLM git SHA
driver
CUDA runtime
Torch
Triton
FlashInfer
Transformers
NCCL
NIXL
Mooncake exact wheel + SHA/CMake flags
model revision
tokenizer revision
chat template
full argv
env vars
TP/DP/EP topology
GPU topology
P/D role
KV connector JSON
```

Metrics snapshot:

- TTFT p50/p90/p95
- TPOT p50/p90/p95
- E2E
- prompt/output throughput
- queue time
- preemption
- KV capacity
- prefix hit
- GPU memory before/after graph capture
- CUDA OOM location
- spec acceptance
- P/D transfer latency

## Phase 1 — Boot compatibility

0.29 `cu129` candidate를 기본으로 시작한다.

목표:

- driver/CUDA variable 최소화
- model load
- tokenizer/template load
- parser registration
- MRV resolved path 확인
- graph compile/capture
- KV cache init
- connector init

이 단계에서는 성능 optimization을 추가하지 않는다.

## Phase 2 — Plain single-engine correctness

P/D와 SD를 끈 가장 단순한 path로 모델 correctness를 확인한다.

Matrix:

- greedy decode
- temperature sampling
- short prompt
- 170K-class long prompt
- 2K output
- stream/non-stream
- reasoning on/off
- tool call on/off

비교는 문자열만이 아니라 token IDs와 structured response를 포함한다.

## Phase 3 — MRV isolation

가능한 모델은 0.29에서:

```text
MRV1 forced vs MRV2 default
```

을 비교한다.

Acceptance:

- exact/near-exact correctness
- memory delta 설명 가능
- throughput/latency regression 없음 또는 근거 있음
- graph mode compatible

MRV2가 production path가 되더라도 MRV1 comparison은 migration 원인 격리에 매우 유용하다.

## Phase 4 — CUDA Graph isolation

순서:

1. eager
2. FULL_DECODE_ONLY
3. PIECEWISE/FULL_AND_PIECEWISE
4. production target

각 step에서:

- post-load memory
- post-profile memory
- post-capture memory
- KV allocation
- graph count/sizes
- first-request compile latency

를 기록한다.

B300은 default capture cap이 다를 수 있으므로 H100/H200 결과를 그대로 복사하지 않는다.

## Phase 5 — Hybrid state/cache

Qwen/Kimi 계열:

- prefix cache off
- prefix cache on + effective cache mode
- retention 0
- dense retention when applicable
- MTP/EAGLE interaction
- long-context repeated-prefix corpus

관측:

- TTFT
- state-cache bytes
- replay work
- hit boundary
- numerical correctness

## Phase 6 — Speculative decoding

각 method를 별도 lane으로 본다.

```text
plain
MTP
DSpark
EAGLE
DFlash where applicable
```

Metrics:

- accepted draft tokens/request
- acceptance rate
- verifier cost
- scheduled tokens/step
- graph batch distribution
- TP communication
- total throughput

0.29의 `--per-request-spec-decode-metrics`는 staging에서 적극 활용한다.

## Phase 7 — P/D

순서:

1. P/D off
2. same-node P/D + NIXL
3. same-node P/D + Mooncake official 0.3.13
4. 필요 시 Mooncake custom minimal 0.3.13
5. hybrid/Mamba model P/D
6. DCP/PCP combination

P/D acceptance:

- 100% response correctness
- no KV lease/transfer leak
- no cuIpc/OpenMem regression
- prefill/decode queue 분배 정상
- transfer latency stable
- cache group/layout compatible
- long-context repeated load 안정

## Phase 8 — TP/DP/EP & communicator

FlashInfer all-reduce A/B:

```text
VLLM_ALLREDUCE_USE_FLASHINFER=0
vs
0.29 default
```

모델별 TP/EP 조합으로 검증한다.

특히 mixed dtype norm/quantized model correctness corpus를 포함한다.

## Phase 9 — Frontend/API E2E

API별:

- Chat Completions
- Responses
- Anthropic Messages via platform adapter
- Cohere if enabled
- rendering endpoint if adopted

Streaming:

- SSE heartbeat
- disconnect/abort
- structured tool arguments
- reasoning boundary
- previous-state/conversation path

## Phase 10 — Overload/failure

- queue saturation
- long-context burst
- prefill OOM
- worker restart
- connector failure
- decode preemption
- router retry
- client disconnect

0.29 admission control은 이 단계에서 검토한다.

## 6. Hardware lanes

## H100/H200

- OpenAI API server MBT default가 0.28 source에서 8192 tier에 남음
- general CUDA Graph cap 512
- Hopper FlashInfer/NCCL path
- current baseline과 가장 직접 비교 가능

## B200/B300

- >=160 GiB branch: online MBT 16384
- Blackwell graph cap 1024
- newer FA4/FlashInfer/CuTeDSL paths
- B300에서 `option omitted`는 H200과 다른 config가 됨

따라서 **모든 performance-critical option은 hardware-independent manifest default로 방치하지 않고 profile별 explicit value**를 갖는 것이 안전하다.

## 8. Rollout gate

Candidate rollout은 다음 순서를 권장한다.

```text
CI image/build
 -> offline benchmark
 -> isolated test namespace
 -> shadow/low-risk endpoint
 -> limited replicas
 -> production canary
 -> broader rollout
```

Go criteria:

- parser regression corpus pass
- model correctness pass
- P/D soak pass
- OOM/headroom budget understood
- SLO regression within agreed range
- no unknown default drift
- rollback image/config ready

---

## 9. Rollback philosophy

Rollback unit은 vLLM package 하나가 아니다.

```text
image + dependency lock + model config + parser config + connector artifact + deployment profile
```

을 하나의 immutable release bundle로 취급한다.

Mooncake wheel이나 FlashInfer만 새 버전으로 남은 채 vLLM만 0.26으로 rollback하면 ABI/behavior가 baseline과 달라질 수 있다.

---

## 10. Final decision

v0.29는 candidate로 평가할 가치가 높다. 그러나 성공 조건은 `0.29 starts and benchmark is faster`가 아니다.

**0.26에서 의도적으로 통제하던 serving behavior를 0.29에서도 설명 가능하게 통제하고, 그 위에 0.29의 새로운 default/optimization을 선택적으로 채택하는 것**이 migration 완료 조건이다.
