# vLLM Stack 진행 계획

작성일: 2026-08-18  
업데이트: Node-local P/D Cell을 0.1.12 이관 전에 구현하는 것으로 순서 변경

## 현재 판단

- `Soomin-Jung/vllm-production-stack-custom`의 `agent/production-0.1.8-baseline-final`은 현재 운영 상태를 보존하는 기준선으로 사용한다.
- 고객 일정 때문에 0.1.12 전체 이관을 먼저 완료한 뒤 P/D를 개발하는 순서는 너무 늦다.
- 따라서 **0.1.8 기준선 위에 Node-local P/D Cell mode를 먼저 추가**한다.
- 다만 P/D orchestration은 0.1.8 Router 기능으로 구현하지 않고, `disaggregated_prefill_orchestrated`를 지원하는 **검증된 0.1.12 계열 LMRouter image를 Cell 내부 전용 Router로 사용**한다.
- Prefill/Decode를 별도 `modelSpec`으로 만들지 않는다. **하나의 modelSpec이 하나의 사용자 모델/Serving Endpoint를 나타내고, P/D는 그 내부 topology로 표현한다.**
- Node-local P/D가 안정화된 후 0.1.12 semantic rebase를 진행하고, 그때 P/D Cell을 범용 Disaggregated Serving 구조로 일반화한다.
- Kimi 계열 멀티노드는 Ray 중심 확장을 장기 정답으로 보지 않고, vLLM native multiprocess + LWS 계열을 목표 runtime으로 검토한다.

## 1. 0.1.8 운영 기준선

### 역할

0.1.8은 더 이상 단순히 "보존만 하는 버전"은 아니다.

현재 운영 기능을 안전하게 유지하면서 **Node-local P/D Cell이라는 제한된 신규 deployment mode까지 추가**한다.

단, 기존 integrated model path를 대규모 수정하지 않는다.

### 원칙

- 기존 integrated model의 rendered manifest를 최대한 그대로 유지한다.
- 기존 Global Router path를 수정하지 않는다.
- P/D 전용 renderer/template을 별도로 추가한다.
- 기존 modelSpec API를 파괴하지 않는다.
- P/D 신규 기능이 기존 모델 rollout을 유발하지 않는지 template diff로 확인한다.

## 2. 하나의 modelSpec 안에서 P/D Cell 정의

사용하지 않을 구조:

```yaml
modelSpec:
  - name: model-prefill
  - name: model-decode
```

채택할 구조:

```yaml
modelSpec:
  - name: qwen36-pd-a
    deploymentMode: pdCell
    replicaCount: 2

    repository: registry/vllm
    tag: v0.26.0-mooncake

    pdCell:
      router:
        repository: registry/lmstack-router
        tag: validated-0.1.12
        port: 8000

      prefill:
        count: 2
        requestGPU: 2
        portBase: 8101
        profile: /profiles/qwen36/pd-prefill.yaml

      decode:
        count: 2
        requestGPU: 2
        portBase: 8201
        profile: /profiles/qwen36/pd-decode.yaml
```

의미:

```text
modelSpec.name      = 하나의 모델 배포 identity
replicaCount        = Cell replica 수
prefill.count       = Cell 내부 Prefill Engine 수
decode.count        = Cell 내부 Decode Engine 수
```

P/D는 모델이 아니라 execution phase이므로 modelSpec identity를 분리하지 않는다.

## 3. Node-local P/D Cell

Cell 하나는 Pod 하나다.

```text
PD Cell Pod
├─ P/D LMRouter :8000
├─ Prefill-0    :8101
├─ Prefill-1    :8102
├─ Decode-0     :8201
└─ Decode-1     :8202
```

P2:D2 / TP2라면 Pod 전체 GPU request는 8이다.

Kubernetes는 Pod를 여러 Node로 쪼개지 않으므로 **Cell의 Node locality는 scheduler hint가 아니라 구조적으로 보장**된다.

`replicaCount`를 늘리면 Cell Pod 자체가 늘어난다.

```text
replicas: 1 → 3

Cell #1 → GPU가 충분한 Node A
Cell #2 → GPU가 충분한 Node B
Cell #3 → GPU가 충분한 Node C
```

Node 이름을 values에 일일이 명시하는 방식을 기본으로 사용하지 않는다.

## 4. Cell 내부 P/D Router

P/D orchestration에는 0.1.12 계열 LMRouter를 사용한다.

```text
routingLogic = disaggregated_prefill_orchestrated
serviceDiscovery = static
```

Cell 내부 endpoint는 localhost로 자동 생성한다.

```text
P = 127.0.0.1:8101, 8102, ...
D = 127.0.0.1:8201, 8202, ...
```

Cell A Router가 Cell B Engine을 선택할 수 없으므로 Node 간 KV transfer가 발생하지 않는다.

기존 Global LMRouter 0.1.8은 Cell 내부 orchestration을 알 필요가 없다. Global Router가 보는 대상은 `Cell Router :8000` 하나의 Serving Endpoint다.

## 5. 기존 운영 연계

실제 inference path:

```text
LiteLLM
  ↓
model-specific P/D Service
  ↓
Cell Router replica
  ↓
Prefill → KV transfer → Decode
```

모델 availability path:

```text
Global LMRouter 0.1.8 /v1/models
              ∩
          LiteLLM /v1/models
              ↓
         vLLM Proxy 노출
```

Cell Pod에는 기존 Global Router discovery label을 적용하고 내부 P/D Engine은 별도 Pod로 노출하지 않는다.

같은 실제 모델을 `qwen36-pd-a`, `qwen36-pd-b`처럼 서로 다른 Kubernetes deployment identity로 동시에 시험할 수 있게 한다.

## 6. Profile 운영

현재 운영의 profile 중심 실행 방식을 유지한다.

```text
/profiles/<model>/pd-prefill.yaml
/profiles/<model>/pd-decode.yaml
```

Engine마다 달라지는 HTTP port, Mooncake bootstrap port 같은 runtime identity는 Helm에서 생성한다.

모델 실행 옵션은 가능한 한 profile이 소유하고 Helm은 다음에 집중한다.

- topology
- P/D count
- GPU resources
- ports
- Router endpoint generation
- scheduling
- labels / observability identity

## 7. Prometheus

P/D Cell에서는 Pod 하나 안에 여러 vLLM process가 있으므로 모든 Engine `/metrics`를 개별 수집해야 한다.

```text
prefill-0 :8101/metrics
prefill-1 :8102/metrics
decode-0  :8201/metrics
decode-1  :8202/metrics
```

기존 `port == 8000` scrape rule만으로는 P/D Engine을 수집할 수 없으므로 P/D 전용 scrape job을 추가한다.

최소 label:

```text
pd_deployment
pd_cell
pd_role
container
node
instance
```

Cell에서는 `instance=PodIP`만 사용하지 않는다. 같은 Pod IP에서 여러 Engine이 실행되므로 `pod/container` 또는 `PodIP:port` 단위로 구분한다.

---

## 8. 장애 정책

초기 구현은 Strict Cell readiness를 사용한다.

```text
Router Ready
AND 모든 P Ready
AND 모든 D Ready
→ Cell Ready
```

하나의 Engine이 죽으면 해당 Cell은 Service에서 빠지고, Kubernetes가 container를 재기동하여 모든 readiness가 복구되면 Cell이 자동 복귀한다.

Cell replica를 2개 이상 배포하여 Cell-level HA를 먼저 확보한다.

부분 Engine 장애에도 살아 있는 P/D로 계속 서비스하는 degraded Cell은 후속 개선으로 분리한다.

## 9. 개발 Gate

### G0 — Baseline regression

P/D 변경 전후 기존 integrated model manifest가 동일한지 확인.

### G1 — P1:D1 render

새 `deployment-pd-cell.yaml`, `service-pd-cell.yaml`, schema 검증.

### G2 — P1:D1 runtime

vLLM 0.26 + Mooncake + orchestrated LMRouter E2E 성공.

### G3 — Variable P:D

P2:D2, P3:D1을 values 변경만으로 생성.

### G4 — Cell replica

Node 이름 없이 `replicaCount` 증가로 Cell scale-out.

### G5 — Stack integration

LiteLLM Service path, Global LMRouter `/v1/models`, vLLM Proxy intersection 확인.

### G6 — Metrics

모든 P/D Engine `/metrics` 개별 scrape.

### G7 — Failure

P/D Router, Prefill, Decode, Cell Pod 장애 후 자동 제외/복귀 검증.

## 10. 0.1.12 이관

Node-local P/D Cell을 검증한 뒤 0.1.12 semantic rebase를 진행한다.

이때 단기 `pdCell`의 contract를 폐기하지 않고 범용 Disaggregated Serving의 node-local topology로 승격한다.

```text
단기 0.1.8
modelSpec.deploymentMode = pdCell
        ↓
장기 0.1.12+
modelSpec.deploymentMode = disaggregated
  └─ topology = nodeLocal | fabric
  └─ prefill pool
  └─ decode pool
  └─ runtime = deployment | nativeMP/LWS
```

즉 단기 구현은 throw-away PoC가 아니라 장기 구조의 가장 작은 실행 가능한 subset으로 만든다.

## 현재 우선순위

```text
최우선  0.1.8 baseline 보호 / regression test
최우선  단일 modelSpec 기반 Node-local P/D Cell renderer
최우선  P1:D1 Mooncake + orchestrated LMRouter 검증
높음    Variable P:D / Cell replica / automatic scheduling
높음    Prometheus / LiteLLM / Global Router 통합
높음    Cell failure/recovery
그 다음 0.1.12 semantic rebase
장기    범용 P/D Fabric + Native MP/LWS
```

핵심 원칙:

> **모델은 하나이고 Prefill/Decode는 그 모델의 실행 phase다. 따라서 하나의 modelSpec이 P/D topology 전체를 소유해야 한다.**
