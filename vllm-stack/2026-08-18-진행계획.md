# vLLM Stack 진행 계획

작성일: 2026-08-18

## 현재 판단

- `vllm-stack-0.1.8`은 **현재 운영 상태를 정확히 보존하는 기준선**으로 마무리한다.
- Prefill/Decode 분리 배포는 이번 주에 **0.1.8에서 최소 동작 검증**까지 진행한다.
- 하지만 P/D Cell, 여러 Prefill/Decode의 독립 확장, 장애 복구, Fabric 구조처럼 앞으로 계속 가져갈 기능은 **0.1.12 기반에서 본격 개발**한다.
- Kimi 계열을 위한 멀티노드 배포는 Ray 중심 구성을 그대로 확장하지 않고, **vLLM native multiprocess 방식의 별도 배포 경로**를 설계한다.

---

## 전체 진행 순서

```text
1. 0.1.8 운영 기준선 확정
        ↓
2. 0.1.8에서 P/D 최소 동작 검증
        ↓
3. 0.1.12 이관 시작
        ↓
4. 0.1.12 기반 P/D 본 개발
        ↓
5. 노드 단위 P/D Cell
        ↓
6. 여러 P / D의 독립 확장 및 장애 복구
        ↓
7. P/D Fabric
        ↓
8. vLLM native multiprocess 기반 멀티노드 배포
```

- Chart 커스텀과 공통 values 반영

### 남은 일

## 2. P/D 분리 배포

P/D는 이번 분기 핵심 과제로 우선순위를 높인다.

### 단계 0 — 최소 P/D 동작 확인

0.1.8에서 가장 작은 형태부터 확인한다.

```text
Router
  ├─ Prefill 1개
  └─ Decode  1개
```

확인할 것:

- 요청 → Prefill → KV 전달 → Decode 전체 경로
- 스트리밍
- 긴 입력 요청
- TTFT / ITL
- P와 D의 GPU 사용량 분리
- connector 초기화 및 KV 전달 오류
- 요청 취소 / timeout
- P 또는 D 재시작 시 동작

여기서는 완성된 플랫폼을 만들지 않는다.

**목표는 코드가 아니라 P/D data path에 대한 확실한 이해와 실측 결과 확보이다.**

### 단계 1 — 0.1.12 기반 Router orchestration

0.1.12의 orchestrated P/D 기능을 기반으로 1P1D를 다시 구성한다.

```text
요청
 ↓
P/D Router
 ↓
Prefill 선택
 ↓
KV / metadata 전달
 ↓
Decode 선택
 ↓
응답
```

이 단계부터 향후 유지할 구현으로 본다.

### 단계 2 — 노드 단위 P/D Cell

하나의 노드 안에서 P/D를 하나의 운영 단위로 본다.

```text
노드
┌─────────────────────┐
│ P/D Cell            │
│                     │
│  Router / Cell Agent│
│      ├─ P           │
│      └─ D           │
└─────────────────────┘
```

검증 항목:

- 노드 단위 배치
- health
- readiness
- P/D 재시작
- 재등록 / 재참여
- connector 복구

### 단계 3 — 비대칭 P/D 확장

```text
P1
P2

D1
D2
D3
```

여기서부터 Prefill 처리량과 Decode 처리량을 별도로 확장한다.

주요 과제:

- P와 D 각각의 부하 기준
- P:D 적정 비율
- dynamic endpoint discovery
- 특정 P/D 장애 시 요청 우회
- 새 Pod 기동 후 자동 재참여

### 단계 4 — P/D Fabric

```text
                 P/D Router
                    │
          ┌─────────┴─────────┐
          │                   │
     Prefill Pool        Decode Pool
   P1 P2 P3 ...         D1 D2 D3 ...
```

필요 기능:

- 동적 멤버십
- health / failover
- P/D 독립 scaling
- topology 인식
- 노드/GPU 배치 정책
- capacity matching
- 새 P/D 자동 등록
- 장애 후 재참여
- 운영 metric / SLO

**이 단계가 최종적으로 원하는 P/D Fabric이다.**

## 3. 0.1.8 → 0.1.12 이관

### 왜 빨리 시작하는가

0.1.12는 단순 패치 버전이 아니다.

0.1.8 이후 Helm 구조, Router, Ray, values/schema, autoscaling, P/D 관련 기능이 크게 바뀌었다.

따라서 0.1.8에서 P/D 기능을 깊게 커스텀한 뒤 0.1.12로 이동하면 같은 일을 다시 해야 할 가능성이 높다.

### 이관 원칙

0.1.8 커스텀을 그대로 복사하지 않고 각 기능별로 판정한다.

```text
유지
상위 버전에서 대체됨
다시 구현
제거
```

예시:

- 공통 env / volume 병합 → 상위 버전 기능으로 대체 가능한지 확인
- GPU resource 기본값 → 유지 또는 재구현
- profile 기반 vLLM 실행 → 재구현 가능성 높음
- `/dev/shm` 정책 → 유지 여부 검토
- Router 운영값 → 유지
- 기존 LMCache 관련 흔적 → 필요성 재판단

### 이관 시작 시점

**0.1.8 기준선이 확정되는 즉시 시작한다.**

P/D Cell/Fabric 본 개발보다 먼저 0.1.12 기반을 확보한다.

## 4. 멀티노드 — Ray → vLLM native multiprocess

### 목적

Kimi 계열 등 대형 모델을 여러 GPU 노드에 배포할 때 Ray를 필수 경로로 두지 않는다.

### 방향

현재 Production Stack의 RayCluster 경로와 별도로 다음과 같은 배포 backend를 검토한다.

```text
vLLM Production Stack
        │
        ├─ 단일 노드 Deployment
        ├─ RayCluster
        └─ Native Multi-node
              ├─ master
              └─ worker
```

필요한 것:

- `nnodes`
- `node-rank`
- `master-addr`
- headless worker
- Pod 간 rendezvous
- 서비스/Pod DNS
- GPU/IB topology
- NCCL / GDRDMA 환경
- master 장애 정책
- worker 재기동 정책
- Kimi 실제 구동/성능 검증

이 작업은 P/D와 구조적으로 분리하되, 0.1.12 기반 Chart 구조에서 같이 수용할 수 있게 만든다.

## 이번 주 목표

### 화요일

- 0.1.8 기준선 PR 검토
- 실제 운영본과 비교 준비

### 수요일

- 모델별 values / profiles까지 기준선 연결
- 0.1.8 P/D 1P1D 형태 구성
- 0.1.12 이관 작업 시작

### 목요일

- 0.1.8 P/D data path 성공 목표
- 긴 입력 테스트
- P/D 장애 / 재시작 테스트
- 0.1.12 커스텀 분류

### 금요일

- 0.1.12 Helm 렌더링 가능한 상태 확보
- 가능하면 0.1.12 orchestrated 1P1D 첫 구동

### 이번 주 성공 기준

이번 주 안에 Production-ready P/D를 만드는 것이 목표가 아니다.

성공 기준은 다음이다.

> **0.1.8 운영 기준선을 고정하고, P/D data path를 실제로 이해·검증한 뒤, 0.1.12 기반의 장기 P/D 구조로 개발 축을 이동시키는 것.**

## 현재 우선순위

```text
최우선  0.1.8 운영 기준선 확정
최우선  P/D 구조 및 data path 검증
높음    0.1.12 이관
중간    P/D Cell / Fabric 본 개발
중간    Kimi용 native multi-node
```

핵심 원칙 하나만 유지한다.

> **0.1.8은 보존하고 검증하는 기반, 0.1.12는 앞으로 개발할 기반으로 사용한다.**
