# Mooncake 0.3.10-post2 폐쇄망 Source Build 계획

작성일: 2026-08-24

## 1. 목표

vLLM image 안에서 `mooncake-transfer-engine==0.3.10.post2`를 source build하여 다음 transport를 모두 포함한다.

- `nvlink`: Multi-Node NVLink(MNNVL)
- `nvlink_intra`: 동일 Node 내부 NVLink/NVSwitch
- `rdma`: 망A IB/GDRDMA 후보
- `tcp`: 기능 검증/비-RDMA fallback

현재 직접 필요한 production path는 망B H200 Node-local P/D의 `nvlink_intra`다. `nvlink`도 함께 빌드하되 MNNVL 전용 transport라는 의미를 유지한다.

이 작업은 P/D Helm PR #2/#4에 끼워 넣지 않고 Dockerfile과 offline source manifest를 다루는 별도 PR로 진행한다.

---

## 2. 발생한 문제와 현재 결론

### CUDA ABI

기존 Mooncake binary와 vLLM image의 CUDA runtime ABI가 맞지 않아 공식 `0.3.10.post2` wheel로 교체했고, 이 단계에서 import/startup ABI 문제는 해소했다.

### transport feature

현재 반입한 wheel에서 `nvlink_intra` 초기화를 시도하면 build에 transport가 없다는 오류가 발생한다. Mooncake source의 해당 feature는 기본 OFF인 compile-time option이므로 pip 재설치만으로 해결되지 않는다.

필요한 build flag:

```text
USE_CUDA=ON
USE_MNNVL=ON
USE_INTRA_NVLINK=ON
```

Mooncake 0.3.10.post2에서:

- `nvlink`는 `USE_MNNVL`로 build한다.
- `nvlink_intra`는 `USE_INTRA_NVLINK`로 build한다.
- vLLM의 `mooncake_protocol` 값은 Mooncake Python binding으로 전달된다.
- 실제 auto-discovered transport는 Mooncake 로그와 runtime selector 환경변수까지 확인해야 한다.

## 3. Version과 ABI 고정

source와 binary identity를 섞지 않는다.

| Layer | 고정 대상 |
|---|---|
| Mooncake source | Git tag `v0.3.10.post2`와 commit SHA |
| Python package | package version `0.3.10.post2` |
| vLLM | 실제 운영 image의 version/commit |
| Python | major.minor와 wheel ABI tag |
| CUDA | toolkit major.minor, runtime library, driver compatibility |
| Compiler | GCC/G++ major, libstdc++ ABI |
| OS | glibc floor와 target architecture |
| GPU | H200 target과 필요한 CUDA architecture |

`main` branch의 build 결과를 `0.3.10.post2` 이름으로 포장하지 않는다. source tag, package metadata, embedded shared object가 하나의 provenance를 가리켜야 한다.

## 4. 최소 build profile

vLLM MooncakeConnector는 `P2PHANDSHAKE` metadata path를 사용하므로, Store/etcd/Go 계열을 무조건 포함할 필요가 없다. 폐쇄망 source closure를 줄이기 위해 먼저 Transfer Engine 중심 최소 build를 시도한다.

```bash
cmake .. \
  -DCMAKE_BUILD_TYPE=Release \
  -DUSE_CUDA=ON \
  -DUSE_TCP=ON \
  -DUSE_MNNVL=ON \
  -DUSE_INTRA_NVLINK=ON \
  -DUSE_ETCD=OFF \
  -DUSE_REDIS=OFF \
  -DUSE_HTTP=OFF \
  -DWITH_STORE=OFF \
  -DWITH_STORE_RUST=OFF \
  -DWITH_EP=OFF \
  -DBUILD_UNIT_TESTS=OFF \
  -DBUILD_EXAMPLES=ON
```

이 명령은 최종 Dockerfile 확정본이 아니라 dependency-minimization baseline이다. 실제 tag source에서 CMake configure, build, wheel packaging, vLLM import까지 통과한 조합만 고정한다.

`BUILD_EXAMPLES=ON`은 image 안에서 `transfer_engine_bench`로 vLLM 이전 transport 검증을 수행하기 위한 선택이다.

## 5. 폐쇄망 반입 단위

외부 GitHub 접근이 없는 build에서 개별 missing dependency를 즉석으로 내려받는 구조를 만들지 않는다. build 입력을 사전에 하나의 source closure로 고정한다.

### 필수 입력

1. Mooncake `v0.3.10.post2` source
2. submodule 또는 vendored third-party source
3. C/C++ build dependency와 development header
4. Python build tool/wheel dependency
5. CUDA toolkit/header/library
6. build script가 간접 호출하는 source archive
7. 각 입력의 version, URL, license, SHA-256

### Go proxy 불확실성 대응

최소 build에서는 Store, etcd wrapper, Go binding을 끈다. 이 조합이 실제로 Go toolchain/module download 없이 완성되는지 먼저 증명한다.

Go가 여전히 필요한 경우에만 다음 중 하나를 택한다.

- 사내 Go proxy를 공식 build input으로 정의
- `GOMODCACHE`를 포함한 vendor bundle을 checksum과 함께 반입
- Go를 요구하는 optional component를 더 제거

원인을 모른 채 build 중 외부 module을 하나씩 추가하는 방식은 재현 가능한 Docker image가 아니다.

## 6. Dockerfile 구조

```text
Stage 1: builder
  ├─ 고정된 OS/CUDA build base
  ├─ 사내 package repository만 사용
  ├─ Mooncake source closure COPY
  ├─ CMake configure/build
  ├─ wheel 생성
  └─ wheel + provenance + validation result 출력

Stage 2: vLLM runtime
  ├─ 검증된 vLLM base image
  ├─ 기존 Mooncake package 제거
  ├─ local wheel 설치 --no-index
  ├─ shared library dependency 검사
  └─ import / transport initialization smoke
```

Dockerfile에는 source URL download를 넣지 않는다. Kaniko build context에 사전 반입한 archive/wheel/source만 넣고, package manager도 내부 repository로 제한한다.

## 7. Transport별 runtime contract

### 동일 Node NVLink/NVSwitch

```yaml
kv_connector_extra_config:
  mooncake_protocol: nvlink_intra
```

```yaml
env:
  - name: MC_INTRANODE_NVLINK
    value: "1"
```

Mooncake 0.3.10.post2는 `MC_INTRANODE_NVLINK`의 문자열 값이 아니라 존재 여부를 검사한다. 끄려면 `0`을 넣지 말고 환경변수를 제거한다.

### MNNVL

```yaml
kv_connector_extra_config:
  mooncake_protocol: nvlink
```

HCA가 보이는 환경에서 MNNVL을 강제하려면 `MC_FORCE_MNNVL=1`을 사용한다. 일반 H200 NVSwitch 단일 Node를 MNNVL로 분류하지 않는다.

### RDMA

```yaml
kv_connector_extra_config:
  mooncake_protocol: rdma
  device_name: validated-device
```

container device, memlock, RDMA device visibility, GDRDMA registration을 함께 검증한다.

### TCP

```yaml
kv_connector_extra_config:
  mooncake_protocol: tcp
```

TCP는 기능 fallback이지 망B 장기-context cross-node P/D의 성능 정답으로 간주하지 않는다. GPU buffer 전송을 위해 Mooncake는 `USE_CUDA=ON`으로 build되어야 한다.

## 8. Acceptance Test

### A. Artifact

- package version이 `0.3.10.post2`
- source tag/commit과 SHA-256 기록
- `ldd` unresolved library 없음
- vLLM runtime Python에서 import 성공
- image 재빌드 후 동일 hash의 wheel 재사용 가능

### B. Transport initialization

각 transport를 별도 process에서 검증한다. Mooncake allocator는 process 전역으로 최초 protocol에 고정될 수 있으므로 한 process에서 protocol만 바꾸며 테스트하지 않는다.

필수 성공 로그:

```text
nvlink_intra → Using Intra-Node NVLink transport
nvlink       → Using cross-node NVLink transport
rdma         → RDMA device 발견과 RDMA transport 설치
tcp          → TCP transport 설치
```

vLLM이 출력한 requested protocol만으로 통과 처리하지 않는다.

### C. Standalone data path

- `transfer_engine_bench` source/target
- GPU buffer registration
- 실제 payload write/read
- payload checksum
- bandwidth/latency
- 동시 transfer

### D. vLLM P/D

1. Qwen3.6-27B P1:D1
2. 2K smoke와 장기 context
3. streaming / non-streaming
4. cancellation / timeout
5. `kv_load_failure_policy: fail`
6. KV transfer success/error metric
7. P/D GPU memory까지 실제 KV가 전달됐는지 확인

Standalone transport가 실패하면 Helm/Router/vLLM 문제로 확대하지 않고 image build 단계에서 중단한다.
