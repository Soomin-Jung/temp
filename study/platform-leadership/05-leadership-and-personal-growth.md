# 리더의 실행과 개인의 성장

## 1. 내가 잘하는 일에서 팀이 잘할 수 있는 일로

깊은 기술 전문성은 리더의 자산이다. 하지만 모든 중요한 판단과 장애 대응이 한 사람을 거치면 팀의 처리량과 성장에 한계가 생긴다.

리더의 성과에는 직접 해결한 문제뿐 아니라 다른 사람이 더 좋은 판단을 하고, 책임 있는 범위를 끝까지 운영하며, 반복해서 결과를 내는 능력을 만든 것도 포함된다.

Technical Leverage는 소수의 공통 개선이 여러 사람의 일을 얼마나 개선하는지를 보는 관점이다. 표준 계약, 검증 도구, 좋은 문서, 재사용 자산과 명확한 책임은 같은 판단을 반복하는 비용을 줄인다. 단순히 일을 더 많이 위임하는 것과는 다르다.

## 2. 깊게 내려갈 때와 위에서 연결할 때

| 상황 | 필요한 행동 |
|---|---|
| 기술적 가능성과 비용이 불확실하다. | 직접 깊이 검토하거나 근거를 검증한다. |
| 여러 팀의 계약과 책임이 어긋난다. | 공통 기준과 의사결정자를 연결한다. |
| 검증된 패턴을 반복 구현한다. | 담당자에게 맥락과 권한을 주고 결과로 리뷰한다. |
| 사용은 적은데 기능 개발이 계속된다. | 고객 문제와 우선순위를 다시 확인한다. |
| 장애가 반복되지만 원인과 책임이 불분명하다. | 구조와 운영 체계를 함께 수정한다. |
| 새로운 기술이 매력적이다. | 고객 가치, 기회비용과 검증 범위를 먼저 정한다. |

리더가 깊이를 유지한다는 것은 모든 구현을 직접 해야 한다는 뜻이 아니다. 판단이 어려운 구간에 전문성을 쓰고, 다른 구간에는 팀이 재현 가능한 기준을 남긴다.

## 3. 팀원의 ownership을 구성한다

기능 이름만 나눠 주면 각자가 컴포넌트의 완성도를 높이지만 전체 사용자 경로는 비어 있을 수 있다. ownership에는 고객, 계약, 운영과 결과를 포함한다.

| 구성 요소 | 담당자가 알아야 할 것 |
|---|---|
| 고객 | 누가 쓰고 무엇을 해결해야 하는가? |
| 결과 | 완료를 어떤 행동과 지표로 확인하는가? |
| 계약 | 앞뒤 시스템과 무엇을 보장하는가? |
| 결정권 | 혼자 결정할 수 있는 범위는 어디까지인가? |
| 운영 | 오류, 지원, 변경과 폐기는 누가 맡는가? |
| 성장 | 다음에 스스로 판단할 수 있어야 하는 것은 무엇인가? |

위임할 때 구현 방법만 전달하지 않고 목적, 제약, 성공 기준과 판단 배경을 전달한다. 결과를 맡긴다면 필요한 정보와 자원도 제공한다. 리더는 전체 연결과 우선순위, 중요한 상충 관계를 책임진다.

## 4. 이해관계자를 연결하는 것도 기술 실행이다

좋은 구조라도 접근 정책, 예산, 제공자의 약속과 운영 인력이 합의되지 않으면 동작하는 제품이 되기 어렵다.

이해관계자의 입장을 다음처럼 나눠 본다.

- 사용자는 자신의 일을 얼마나 쉽게 끝낼 수 있는지 본다.
- 서비스 책임자는 품질, 지원과 변경 위험을 본다.
- 운영자는 복구 가능성과 반복적인 부담을 본다.
- 재무 책임자는 비용의 근거와 예측 가능성을 본다.
- 조직 리더는 투자 대비 가치와 책임 있는 확산을 본다.

이들의 목표는 완전히 같지 않다. 리더는 어느 한쪽의 언어만으로 결론을 내리지 않고 선택의 효과와 비용을 설명한다. 예외를 허용하면 유연성이 늘지만 운영 부담이 커질 수 있다는 식으로 trade-off를 드러낸다.

## 5. 보고는 판단할 수 있는 증거를 전달한다

| 질문 | 보고에 넣을 내용 |
|---|---|
| 왜 필요한가? | 고객 문제와 영향의 근거 |
| 무엇이 달라졌는가? | 사용자의 행동과 운영 결과 |
| 효과가 있는가? | 기준선과 비교, 측정 한계 |
| 무엇이 불확실한가? | 가정, 위험과 아직 검증하지 못한 것 |
| 무엇을 결정해야 하는가? | 선택지, 비용, 권고와 필요한 자원 |

기술 상세는 판단을 뒷받침할 위치에 둔다. 먼저 결과와 투자 이유를 설명하고 필요한 경우 구현 근거로 내려간다. 측정하지 않은 성과를 보고용 숫자로 만들어서는 안 된다.

**위에서는 고객과 사업의 언어로 설명하고, 필요하면 시스템의 제약까지 내려가 판단을 검증하는 것**이 기술 기반 플랫폼 리더의 강점이다.

## 6. 세 축의 성장 계획

| 축 | 연습할 것 | 성장의 증거 |
|---|---|---|
| Technical Depth | 핵심 경로의 제약과 실패를 구조적으로 설명한다. | 기술 선택의 근거와 검증 가능한 계약 |
| Product Thinking | 사용자 여정을 관찰하고 작은 가설을 시험한다. | 반복 사용, 빠른 첫 가치와 우회 감소 |
| Business Acumen | 비용·편익·책임과 자원 배분을 연결한다. | 근거 있는 투자 제안과 범위 결정 |
| Leadership | 판단을 전달하고 다른 사람이 책임지게 한다. | 팀이 독립적으로 결정하고 운영하는 범위 확대 |

모든 분야의 전문가가 될 필요는 없다. 재무, 보안, 업무 도메인 전문가와 정확하게 협력할 수 있는 질문과 연결 능력을 키운다.

학습도 산출물에 연결한다. 용어를 외웠으면 지표 정의서를 쓰고, 제품 사고를 배웠으면 실제 사용자 여정을 확인하고, 경제성을 배웠으면 가정이 드러난 비용 모델을 작성한다. 개념이 행동으로 바뀌어야 성장의 증거가 남는다.

## 7. 반복해서 점검할 질문

- 이번에 고른 문제는 고객에게 중요한가, 내가 잘 아는 기술이라 선택했는가?
- 기능 완료 이후 실제 사용과 지원까지 확인했는가?
- 새 책임을 맡을 권한과 자원이 있는가?
- 내 개입 없이 팀이 판단할 수 있도록 맥락을 남겼는가?
- 숫자가 좋아진 이유와 나빠진 결과를 함께 보았는가?
- 불필요해진 기능이나 투자 방향을 종료할 수 있는가?
- 고객이 플랫폼을 선택하는 이유를 내 설명 없이 말할 수 있는가?

성장은 직함을 바꾸는 것으로 확정되지 않는다. 중요한 문제를 고르고, 합리적인 구조를 만들고, 팀과 함께 제공하고, 결과에 따라 다음 결정을 바꾸는 반복에서 드러난다.

이번 깨달음을 유지하는 방법은 과거의 기술적 성취를 낮춰 평가하는 것이 아니다. 그 깊이가 더 넓은 고객 가치로 연결되도록 매번 판단의 범위를 확장하는 것이다.
